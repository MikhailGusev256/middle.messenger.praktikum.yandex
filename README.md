# Messenger

Учебный проект — веб-приложение мессенджера

Стек: Vite + TypeScript + Handlebars + Sass, WebSocket для сообщений. Тесты — Vitest (+ jsdom).

Интерфейс взят из готового макета: [Figma](https://www.figma.com/design/jF5fFFzgGOxQeB4CmKWTiE/Chat_external_link?node-id=0-1)

## Функциональность

- Регистрация, вход и выход из системы (cookie-сессия [ya-praktikum API](https://ya-praktikum.tech/api/v2/swagger/#/))
- Настройки профиля: изменение данных, пароля и аватара
- Чаты: список чатов пользователя, создание чата, добавление и удаление участников
- Обмен сообщениями в реальном времени через WebSocket: история чата подгружается при его открытии и переживает перезагрузку страницы
- SPA-роутер с историей браузера (кнопки «Назад»/«Вперёд», F5 сохраняет страницу) и проверкой авторизации: неавторизованным доступны только `/` и `/sign-up`

## Страницы

| Маршрут      | Страница                 |
| ------------ | ------------------------ |
| `/`          | Авторизация              |
| `/sign-up`   | Регистрация              |

| `/404`       | Ошибка 404               |
| `/500`       | Ошибка 500               |

## Архитектура

- Собственный класс-компонент `Block` (Handlebars-шаблоны, реактивные пропсы, lifecycle-хуки)
- Реактивный store + `connect` для подписки компонентов на состояние
- HTTP-клиент на XHR + Promise (`GET/POST/PUT/DELETE`, query string для GET, JSON/FormData для остальных)
- Транспорт WebSocket (`src/utils/ws.ts`) не знает о протоколе чата: типы кадров (`message`, `get old`, `ping`) живут в `MessageService`
- Слои: форма → сервис → API-клиент → store → connect → UI

Пользовательские данные попадают в разметку только через экранирующий `{{ }}` Handlebars — это защита от XSS. Тройные скобки `{{{ }}}` используются исключительно для вызова вложенных компонентов.

## Команды

```bash
npm install     # установка зависимостей
npm run dev     # запуск дев-сервера с HMR (http://localhost:3000)
npm run build   # сборка проекта в dist/
npm run start   # сборка и запуск превью продакшен-сборки (http://localhost:3000)
npm run lint    # prettier + tsc + stylelint + eslint
```

Требуется Node.js версии 22 или выше. Для воспроизводимой установки — `npm ci`.

## Тесты

Тесты написаны на [Vitest](https://vitest.dev/) и лежат рядом с тестируемыми модулями (`*.test.ts`).

npm test          # watch-режим
npm run test:run  # однократный прогон (CI, precommit)

## Деплой

Проект развёрнут на Netlify: https://dapper-snickerdoodle-50ee4d.netlify.app/

### Как приложение обращается к API (и почему по-разному в dev и prod)

Сессия в API практикума — cookie-based, а кука выдаётся для домена `ya-praktikum.tech`. Поэтому вопрос «на какой origin отправлять запрос» решается по-разному в двух окружениях; развилка живёт в одном месте — `src/api/constants.ts` (`import.meta.env.PROD`).

|                      | HTTP                           | WebSocket                              | Кука                                                         |
| -------------------- | ------------------------------ | -------------------------------------- | ------------------------------------------------------------ |
| dev / `vite preview` | свой origin → vite-прокси      | свой origin → vite-прокси (`ws: true`) | first-party, `Domain` вырезается через `cookieDomainRewrite` |
| production (Netlify) | напрямую в `ya-praktikum.tech` | напрямую в `wss://ya-praktikum.tech`   | third-party, `SameSite=None; Secure`                         |

Причина различия в том, что **Netlify не проксирует WebSocket** — ни через `[[redirects]]`, ни через edge-функции: их модель «`Request` → `Response`» не допускает смену протокола (см. [ограничения edge-функций](https://docs.netlify.com/build/edge-functions/limits/)). А токен сокета сервер проверяет вместе с кукой сессии, поэтому подключаться к практикуму, имея куку на домене Netlify, бессмысленно — HTTP и WebSocket обязаны ходить на один и тот же origin.

**Известное ограничение прод-сборки:** так как запросы идут на чужой домен, сессионная кука является сторонней. Если в браузере отключены сторонние куки (настройка «Блокировать сторонние файлы cookie», режим инкогнито, настройки по умолчанию Safari и Firefox), вход не выполнится — API ответит `Cookie is not valid`. Лечится разрешением сторонних кук для `[*.]ya-praktikum.tech` либо запуском проекта локально (`npm run dev`), где всё идёт через прокси и кука first-party.

Следствие для кода: `xhr.withCredentials = true` в `src/utils/http.ts` в прод-сборке обязателен — без него браузер не приложит куку к кросс-доменному запросу.
